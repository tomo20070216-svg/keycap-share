## データ設計の要点(出典: plan.md 4章)

- `keyboards`: 機種名、物理レイアウト(左右のキー位置・サイズ、親指キー位置、キー数)
- `layouts`: 機種参照、タイトル、説明文(なぜこの配置か)、投稿者、作成/更新日時、公開URL用ID
- `layers`: 配列参照、レイヤー番号、レイヤー名
- `key assignments`: レイヤー参照、キー位置ID、表示用の名前
- `tags`: 配列との多対多

割り当ての値は表示用の名前(文字列)。実際のテーブル定義はAIが提案し、人間の承認を得てから確定する(未確定事項)。

## Xログインの調査結果(2026-09-28、P0-6)

**結論: 「完全無料」とは言い切れない。少額の従量課金が発生する可能性が高く、人間の承認(支払い方法の登録)が必要になる。**

- Xの開発者向けAPIは2026年2月6日に「pay-per-use(従量課金)」方式に一本化され、**新規開発者向けの無料プランは廃止された**。サブスクリプションはなく、投稿の作成($0.015/件、リンク付きは$0.20/件)や投稿の取得($0.005/件)などがクレジット制で課金される。([X API pay-per-usage pricing and credits](https://docs.x.com/x-api/getting-started/pricing)、確認日2026-09-28)
- SupabaseはX/Twitter OAuth 2.0プロバイダーを2026年2月6日に追加しており、比較的新しい機能。ログインの実装手順自体は公式ドキュメントにあるが、料金・アカウント種別についての記載はない。([Sign in with X / Twitter | Supabase Docs](https://supabase.com/docs/guides/auth/social-login/auth-twitter)、[X / Twitter OAuth 2.0 is now available for Supabase Auth](https://supabase.com/blog/x-twitter-oauth-2-provider)、確認日2026-09-28)
- **未確定点**: ログイン(OAuth認可・トークン交換)そのものが課金対象かは公式ドキュメントで明言されていない。ただし、ログイン後に「投稿者名」を表示するためにユーザーのプロフィール情報(ユーザー名・表示名)を取得するAPI呼び出し(`/2/users/me`相当)は、通常の読み取りAPIと同様に課金対象になる可能性が高い(1回あたり$0.001〜$0.005程度と推定されるが、公式の確定情報は見つからなかった)。
- 参考として調べた二次情報(Blotato、Postproxyなどの非公式まとめサイト)には「OAuthはFree/Basic/Proいずれのプランでも利用可能」という記述もあったが、日付や一次情報源が不明瞭で、2026年2月の従量課金化以降の情報として信頼できるか確認できなかった。**この点は二次情報のみで、公式ドキュメントでは確認できなかった。**

**推奨する進め方(要人間の承認):**
1. Xの開発者コンソール(console.x.com)でアプリを実際に登録し、ログインのみを試して、その時点で課金が発生するかをコンソール上の請求画面で確認する(登録自体は人間が行う。`docs/safety.md`の「法的な同意」に該当)。
2. 従量課金が発生する場合、想定される投稿数・ログイン数に対して費用が小さいか(月数百円程度に収まるか)を確認してから、支払い方法の登録(人間の承認が必要)を判断する。
3. 費用や手間を避けたい場合は、代替案「ログインなし+編集用の秘密キー付きURL」に切り替える。データ設計(フェーズ1)では、どちらでも対応できるよう「投稿者を識別する情報」を抽象化しておく。

## 決定: 投稿者識別の方式(2026-09-28)

**「①ログインなし+編集用の秘密キー付きURL」を採用する。** Xログイン(フェーズ6)は見送り、`plan.md`のフェーズ4(X共有ボタン)は影響を受けない(共有ボタンはXの開発者アカウント・APIが不要なため、これとは無関係に進める)。

- 新規投稿時、編集用の秘密キー(例: ランダムなトークンを含むURL)を発行し、投稿者はそれをブラウザに保存しておくことで、後から自分の投稿を編集・削除できる。
- 「投稿者名」は自由入力のニックネーム欄とする(Xアカウントとの連携なし)。
- フェーズ6の「自分の投稿だけ編集できる」という完了の目安は、秘密キーの一致で判定する形に変更する。

## VercelとSupabaseの無料枠調査(2026-09-28、P0-7)

**結論: 現時点の想定規模(個人プロジェクト、非商用)であれば無料枠で運用できる見込み。ただし2点、事前に知っておくべき制約がある。**

### Vercel(Hobby プラン)

出典: [Limits](https://vercel.com/docs/limits)、[Fair Use Guidelines](https://vercel.com/docs/limits/fair-use-guidelines)(確認日2026-09-28、ページの最終更新表記は2026-09-16/09-14)

| 項目 | Hobbyの目安上限 |
|---|---|
| Fast Data Transfer(転送量) | 月100GBまで |
| Function実行回数 | 月100万回まで |
| Function実行時間(Active CPU) | 月4時間まで |
| Image Optimization変換 | 月5,000回まで |
| デプロイ回数 | 1日100回まで |
| Functionの最大実行時間 | デフォルト10秒、最大60秒 |
| プロジェクト数 | 200まで |

- **超過時の挙動**: Hobbyプランには支払い方法の登録がなく、従量課金の自動請求は発生しない。上限を大きく超える使い方をすると、Vercelから利用是正の連絡が来る、または利用が制限される(Fair Use Guidelinesに基づく)。「気づかないうちに課金される」心配は基本的にない。
- **重要な制約(見落としやすい)**: **Hobbyプランは「非商用の個人利用限定」**。寄付(donation)の受け付けはHobbyでも可だが、広告掲載・決済処理・有償で作成/運用する行為は「商用利用」とみなされ、規約上Pro以上のプランが必要になる。このプロジェクトは現時点で非商用なので問題ないが、将来的に収益化する場合は要注意。
- OGP画像生成(`ImageResponse`)はVercelの「Image Optimization」とは別のFunction実行としてカウントされる見込み(要フェーズ4での実測確認)。

### Supabase(Free プラン)

出典: [Supabase Pricing](https://supabase.com/pricing)(確認日2026-09-28)

| 項目 | Freeの上限 |
|---|---|
| データベース容量 | 500MB |
| ファイルストレージ | 1GB |
| 月間アクティブユーザー数(MAU) | 50,000人 |
| エグレス(データ転送量) | 5GB |
| APIリクエスト数 | 無制限 |
| 同時に有効化できるプロジェクト数 | 2つまで |

- **重要な制約(見落としやすい)**: **1週間アクセスがないとプロジェクトが自動的に一時停止(pause)される。** 再開は手動でダッシュボードから行えるが、公開直後にアクセスが少ない時期は要注意。長期間放置する可能性があるなら、定期的にアクセスする仕組み(監視サービスでの定期pingなど)を検討する。
- 上限(500MB DB、5GBエグレスなど)を超えた場合の自動課金の可否は、公式ドキュメントで明記された記述を確認できなかった。Pro以上のプランには「Spend caps(使用上限)がデフォルトでON」という記載があり、無料プランでも同様に上限で止まる設計と推測されるが、**未確定**。実際に上限に近づいたら、Supabaseダッシュボードの使用量画面で都度確認することを推奨する。

### 総合判断

- 今回のMVP規模(個人利用、投稿数が数百件程度を想定)であれば、両サービスの無料枠に収まる可能性が高い。
- 唯一注意すべきは、**Supabaseプロジェクトの「1週間放置で自動停止」**。公開後しばらくアクセスが少ない場合に備え、フェーズ6(運用)で軽い対策(定期アクセスの仕組みなど)を検討する。
- Vercelの「非商用限定」は、現在の計画(広告や課金なし)であれば問題にならない。

## 追加要件: 配列の「コピーして編集」機能(2026-09-28、人間の要望により追加)

`plan.md`には未記載の新規要件。**他の人の配列を元に、自分用に配置を一部変えて投稿したい**というニーズ(例: Mac用の配列をコピーし、Windowsキーだけ差し替える)。

- 他人の配列の閲覧ページに「この配列をコピーして編集」ボタンを置く。
- 押すと、その配列の内容(機種・レイヤー・キー割り当て)を複製した新しい配列がエディタで開かれる状態になる。
- 保存すると、複製元とは別の新しい配列として、新しい公開URL・新しい編集用秘密キーが発行される。
- 複製元への参照(「〇〇さんの配列を元にしています」のようなリンク)を残すと、元の投稿者への敬意にもなり、親切な設計になる。ただし必須にはしない(複製元が削除されている場合もあるため)。
- ログイン方式(秘密キー付きURL)と組み合わせても問題なく実現できる。
- フェーズ5(投稿エディタ)の要件に追加する。データ設計(フェーズ1)では、「複製元の配列ID」を保持できる項目を検討する。

## 追加要件: コンボとマクロの表示(2026-09-28、人間の要望により追加)

`plan.md`には未記載の新規要件。Orca echoはファームウェアにZMKを使っており、Keychron Launcherでキー配置・レイヤー・コンボ(複数キーの同時押し)・マクロ(一連のキー操作を1つのキーに登録)を設定できる([KeyLab DB](https://www.keylabdb.com/en/blog/featured-keyboard-keychron-orca-echo)、確認日2026-09-28)。これらも配列の一部として共有できるようにする。

- **マクロ**: キーには短い表示名(例: `署名`)を表示する(既存の割り当てのまま表現できる)。キー図の下に「マクロ一覧」を置き、中身を文章で説明する。具体的なキー操作の手順は記録しない(`plan.md` 方針4「表示用の名前」に合わせる)。
- **コンボ**: キー図の下に「コンボ一覧」を置く(例: `① J + K → 左クリック`、対象レイヤー)。キー図上では対象キーの隅に番号①②…を付けて一覧と対応させる。線で結ぶ表示はキーが込み合うため採用しない。
- データ設計(スキーマ・テーブル追加)は `tasks.json` P2-5、表示は P2-6。
- 人間の実例(テストデータに使う): J+K → 左クリック、K+L → 右クリック、J+L → ホイールクリック。

## キー図の表示方針(2026-09-28、人間の決定)

- 1つの要素に複数の操作がある場合、キーはタップを大きく、長押しを下に小さく表示する。ダイヤル・トラックボール・スクロールパッドは要素の周りに小さく並べる。
- レイヤーで割り当てのないキーは、空欄+薄い灰色で表示する。
- フェーズ2では全レイヤーを縦に並べて表示する(タブ切り替えはフェーズ3の閲覧ページで検討)。
- 座標は、実機写真から推定して人間が実機と見比べて確認する(定規での計測は行わない)。確認が取れるまで「仮の値」表記を維持する。
